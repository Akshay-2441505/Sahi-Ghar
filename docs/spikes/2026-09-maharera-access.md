Run on: 2026-09-21   By: Claude, with the project owner's approval   From: the owner's Windows 11 machine on its normal internet connection (network/location not recorded)
Spec: docs/superpowers/specs/2026-09-21-sahi-ghar-design.md §3
Evidence: `spike/samples/` (raw responses, certificate PDFs, one browser observation). Tool: `spike/probe.py` (honest User-Agent naming the project and the owner's contact, one request at a time, at least 3 s apart).

## Summary

- **Open, no CAPTCHA, server-rendered, plain GET pagination** (main site `maharera.maharashtra.gov.in`): the project list (49,450 projects), the promoter search, the promoter complaint report (5,382 promoters with complaints) and each promoter's complaint list, plus the registration and extension **certificates** (PDFs with a text layer) via `project-document`.
- **CAPTCHA-gated** (second host `maharerait.maharashtra.gov.in`): the project **detail** view, which every "View Details" link points to. Stopped there, nothing attempted.
- **What that means:** complaints, promoter names, registered-office addresses, and *original and extended registration end dates* are available from open pages. PAN, partners/directors, a promoter's past-experience list, actual completion status and quarterly progress reports are not (they live behind the CAPTCHA).
- **Design consequences** (see "Findings that change the design" and the Decision): the delivery-history metric must be redefined around registration extensions, not actual completion; the grouping rules in spec §6 cannot fire on open data as written; complaint "resolved" is not what the site's statuses mean.

## Findings that change the design

1. **Delivery history cannot use actual completion.** No open page gives an actual completion date or a "completed" flag. What open data does give is the original registration end date and, where an extension certificate exists, the extended end date. A defensible open-data metric is: *registered end date, extended by N months (or not extended), and whether the current end date has passed*. Spec §7 (on time / late / overdue against an actual completion date) needs redefining before Plan B.
2. **Complaint statuses are not open/resolved.** Across 28 complaints on 10 promoters the statuses were "Order Approved" (26), "Roznama Approved" (1) and "Hearing Scheduled" (1). "Order Approved" means an order was issued, not that the buyer's problem was resolved. 5 of 28 also had "applied for non-execution = Y" (a buyer asked to enforce an order the promoter had not complied with), which is a stronger signal than the status itself. The `open | resolved` column and the complaint sub-score in spec §7 need remapping (pending vs order issued vs order not executed). Small sample; the full status vocabulary is unknown.
3. **Complaints join to projects by registration number, not by name.** The complaint detail lists "Project No." (a `P5…` registration number), so complaint-to-project matching is exact. Promoter identity is weaker: project cards carry the promoter's name only (no promoter ID), while complaint pages carry the site's `promoter_id` and a name.
4. **Grouping rules cannot fire on open data.** Spec §6 needs PAN (for `filing_confirmed`) or overlapping partners/directors (for `possible`); neither is on open pages. Open data has promoter name, registered-office address (in the certificate), and pincode. Groups would all be single promoters unless a rule based on same registered-office address plus similar name is added (a `possible` link, still excluded from the score).
5. **Refresh strategy:** the card's `Last Modified` date and extension-certificate presence allow incremental refresh; a full weekly crawl of certificates is not needed.

## Karnataka and Telangana (shallow check)

Same polite rules (one request at a time, at least 3 s apart, honest User-Agent), 8 requests in total to those sites (plus one read of the rera-india GitHub page). The three big Karnataka samples are saved **truncated** (`*.head-only.html`, with the original size noted at the end of each file); their full sizes were 6.4 MB, 17 MB and 0.7 MB.

**Karnataka (`rera.karnataka.gov.in`): reachable, no CAPTCHA on the pages checked, and unusually bulk-friendly.**
- `/promoterComplaintReport`: one server-rendered table with **all** promoters on one page ("Total Complaints : 13289 Total Promoters : 2018"), each row linking to `complaintReportWiseList?pName=<opaque encrypted token>`. The same builder appears under several spellings ("... Private Limited", "... Private limited.", "... Pvt Ltd"), which is direct evidence that promoter-name normalisation matters.
- `/viewRenewalProjects` (project extension status): **structured tables with old and new registration numbers, promoter, project, district, application date, `OLD COMPLETION DATE`, `NEW COMPLETION DATE` and approved date** (about 3,900 rows across three tables, including a rejected-extensions table), plus links to old and extension certificates (`/certificate?CER_NO=...`, `/extensionCertificate?CER_NO=...`). This is exactly the original-versus-revised completion data, as structured columns rather than PDFs.
- `/viewAllProjects` (project status) is a tabbed page. It shows counts and links to lists, including "List of Projects Applied for Project completion: 3526" (`/viewAllCompletedProjects`), "applications Rejected: 957" and "Withdrawn/Revoked: 107". The completion list is a candidate actual-completion signal that Maharashtra's open pages lack; its columns were not inspected. The main registered-projects tab structure was not fully mapped.
- Also linked from the home page: orders and judgements search, project-wise complaint report, default project list, daily cause lists. Not inspected.
- `mahitikanaja.karnataka.gov.in/Rera/GetProjectDetails`: a state open-information portal with a Year/District/Status query form that uses a **server-side CAPTCHA**; not pursued.
- Not verified: promoter PAN (DATA_SOURCES.md claims it), quarterly progress reports, and whether any Karnataka detail view is CAPTCHA-gated.

**Telangana (`rera.telangana.gov.in`): home page reachable; project search not reachable from this machine.**
- The home page links to "Search Registered Projects and Agents" on a different host, `rerait.telangana.gov.in/SearchList/Search` (11,216 registered projects and 5,255 agents shown on the home page, plus 11 revoked). **TLS verification failed** from this machine ("root certificate which is not trusted by the trust provider"). Verification was not bypassed, so the project search could not be inspected. It may be a certificate-store issue specific to this machine; it needs to be re-checked (for example from a browser, or with the government root certificate installed) before anything is assumed.
- `complaints-rera.telangana.gov.in` is a complaint **filing and status-tracking portal** (login, registration, hearing instructions). No public promoter complaint list was found on its home page, so DATA_SOURCES.md's "complaints and litigation history, including order/judgment records" for Telangana is **unconfirmed** and may sit behind a search or a login.
- Orders by TG-RERA (Authority, Adjudicating Officer, REAT, suo motu) are linked from the home page as document listings; not inspected.

**Does the adapter interface (`discover()` + `parse()`) need reshaping for slice 2?** No. Both states fit: Karnataka's bulk pages are simply fewer, larger `RawDoc`s, and Telangana's unknowns are about access, not shape. One addition worth making in Plan B: `RawDoc` may carry very large bodies (17 MB seen), so the raw store should stream to disk rather than hold everything in memory.

## Decision

The RTI request continues in parallel as an optional second source. See `docs/plan-b/crawler.md`.

> *Superseded, as first recorded that day:* **Path B (official data only). The program will not crawl any RERA site.** The Path A analysis below is kept because it shows which fields the open pages contain, which is what the data request should ask for and what the import adapter should expect. See "Owner's decisions" at the end.

Applied the spec's rule (§3): Path A = open pages fetched by the program; Path B = official data / data request / assisted import; Mixed = each per data type.

- **Project data (Maharashtra): Path A, conditional on the runner check** (Task 3, Step 3). Registration number, project name, promoter name, district, pincode, `Last Modified`, and the **original and extended registration end dates** (from the registration and extension certificates) are on open pages (rows 1-5). **Gap:** actual completion status/date is not on open pages; for that one field the options are Path B (a data request or RTI to MahaRERA) or leaving it out. It is not needed if the delivery metric is redefined (decision 1 below).
- **Promoter data (Maharashtra): Path A for name and registered-office address** (from the list and the certificates). **PAN, partners/directors and any past-experience list: not available on open pages** (they sit behind the detail-app CAPTCHA, row 1). Leave them out of slice 1; revisit through Path B or MCA data (slice 5).
- **Complaint data (Maharashtra): Path A.** Promoter complaint list plus per-promoter detail, each complaint carrying a project registration number (rows 1, 4).
- **Scheduled runner: undecided** until the runner check runs (Task 3, Step 3). Fallback if GitHub is blocked: run the weekly job from the owner's machine or a small VM. Either way the crawler must handle the missing intermediate certificate (row 7) without disabling TLS verification.
- **Karnataka and Telangana:** Karnataka looks like the easier state (bulk server-rendered tables, structured old/new completion dates, a completion-applied list). Telangana is **not determined** (project-search host failed TLS trust from this machine; complaints site is filing-only). The adapter interface needs no change for either.
- **Rationale:** rows 1-5 show that everything needed for complaints, project identity, and original-versus-revised end dates is open and enumerable with plain GET requests (about 50,000 projects at 10 per page), and the only CAPTCHA seen guards the detail app, which is left alone. Row 7 shows the site tolerated a polite rate with an honest User-Agent. Row 8 shows the terms are silent on automated access and the copyright policy asks for accurate, non-misleading reuse with the source acknowledged, which matches the product's source-link and timestamp rules.
- **Consequences for the Plan B adapter:**
  - Available for scoring: original registration end date, extended end date (if any), extension presence, complaint list with year/month and status, non-execution flags, promoter name and address, `Last Modified`.
  - Available for grouping: promoter name, registered-office address, pincode. **Not available:** PAN, partners/directors. So spec §6's `filing_confirmed` and `possible` rules cannot fire as written.
  - Not available anywhere open: actual completion date and "completed" flag; quarterly progress reports (slice 3 needs a separate look).
  - Refresh should be incremental (use `Last Modified` and extension-certificate presence); certificates are about 200 KB each, so a full re-crawl is about 41 hours at the polite rate.
  - The raw store must stream large bodies to disk (Karnataka pages reach 17 MB).

### Owner's decisions (2026-09-21)

1. **Delivery-history metric: registration end dates. Approved.** Show "registered to <date>, extended by N months (or not extended)" and whether the current end date has passed, instead of on time / late against an actual completion date. Caveats to keep in the wording: an extension is not necessarily the promoter's fault (regulators have granted blanket extensions), and a project past its end date with no extension may simply have been completed, so "past end date" is never called "late".
2. **Automated crawling: no. Official data only (Path B). Approved, then reversed.** *Reversed later the same day: the owner approved crawling the open pages politely, trial first (see the note at the top of this section).* As first decided: Consequences: the Plan B "adapter" is a **file-import adapter**, not a crawler; the weekly-scrape workflow and the GitHub runner reachability check (question 6) are no longer needed; the raw store and the source-link/timestamp rules still apply (each imported file is a `source_document`).
3. **Complaint wording and grouping: defaults chosen by Claude, not yet reviewed by the owner.** Complaint stages replace open/resolved (order issued; hearing pending; order not executed when "applied for non-execution" is Y), and "unresolved" = pending or not executed. Grouping adds a `possible` link on *same registered-office address plus similar promoter name* alongside the PAN and partner rules, which simply stay dormant until such data arrives. Both are reversible when the owner reviews them.
4. **History rewrite: approved and done.** A third-party map API key had been saved in a sample and was in an earlier local commit; the local branch history was rewritten (tree verified identical) and the old objects purged. Nothing had been pushed.

### What "official data only" leaves to do

- **The Unified RERA Portal is not a data source today.** `rera.mohua.gov.in` (launched 4 Sep 2025 by the Housing Ministry) was checked with one request: its home page is an information site (the Act, notifications, an implementation-status tracker with counts, and a state-facing login). **No project search and no dataset download were found**, despite blog posts describing a searchable national database. Not ruled out: features behind the login or on other pages. `data.gov.in` showed no RERA dataset in a web search.
- **The realistic official route is a written data request or RTI to each state RERA** (MahaRERA has an RTI section linked from its site). The request should name the fields this spike found: registration number, project name, promoter name and registered office, registration start and end dates, extension certificates and new end dates, complaint number, project number, filing year/month, status, non-execution flags; and, if they are willing, the fields the open pages lack: promoter PAN, partners/directors, actual completion date and status. Draft it once the owner decides who files it.
- **Open question for the owner:** *human-assisted import*. A person saving pages from the official site in their own browser (for example Karnataka's single-page promoter complaint table and extension table, which hold thousands of rows) and feeding the saved files to the import adapter is a form of Path B in the spec. It is not automated crawling, but it was not covered by the owner's answer, so it is **not** assumed.
- **Until data arrives, everything is built and tested on fixtures**, including the real page formats captured in `spike/samples/`.
